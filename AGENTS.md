# Repository collaboration

- For Rubber Duck Pool environment and prop art, consult `projects/rubber-duck-pool/docs/asset-art-direction.md`. The deck chair is a visual reference, not a requirement to repeat its exact colors or details on every asset.
- When creating or updating a pull request, write a specific title and a meaningful description based on the final changes. Do not leave a branch name as the title or the description empty. Explain the user-visible problem or outcome, summarize the material changes, and report checks run and important limitations. Keep the title and description current if scope changes. Do not claim a check was run when it was not.
- Follow `.github/pull_request_template.md` when it applies, adapting the detail to the change. Creating a PR does not imply permission to merge it.

- **Main implementation: Claude Opus 5.5 (max) and Gemini 4 Neon (high).** They write the large structure: features across several files, structural changes, and changes to shared `packages/`. Opus also directs: it checks diffs, runs `npm run verify`, lands, pushes and reports.
- **Side implementation: GPT-6.1 Terra (max) and Gemini 4 Hydrogen (extra).** Inside the structure the main implementers set, they write small-scope code: one-file cleanups, performance touch-ups and nearby fixes.
- **Assets: GPT-6.1 Terra (max).** 3D modeling and asset rendering in Blender.
- **Checks: the code's owner.** The model that writes the code (Opus, Neon, Terra or Hydrogen) writes its check in the same run, while it holds the context: a test that fails on the code before the change, refined until it catches what the owner would flag. A check that calls for a reviewer says why.
- **Records: GPT-6.2 Sol (medium).** From the diff and the owner's report only, it writes the entries in `docs/worklog.md` and the project's `improvements.md`.
- **Review: Opus and Neon review each other's code.** Neither reviews its own. The reviewer also checks that each new test fails on the code before the change.
- **Flow:** Astra plans; Opus or Neon builds the structure and its checks, with Terra or Hydrogen on the side units and theirs; Sol records; the other main implementer reviews; Opus verifies, lands and pushes.
- **Briefs.** Each role's standing brief is in `docs/agents/`: `plan.md` (Astra), `unit.md` (every code unit), `review.md` (Opus and Neon), `records.md` (Sol). Append it to the unit's own brief.
- **Delegating.** Name the model, and pass the materials, the question and the definition of done. Do not do the same work twice or delegate it again. If a named model cannot be used, say so and continue the work that can be done.

# How we write code

The user's working rules (2026-11-20, after @poteto). They bind every model that writes or reviews code here.

- **Proof is running it.** A change is done when its author ran the real thing and saw it work: the page through the verify skill's drives, a library through `node -e` or its tests, a number measured before and after under the same conditions. "It compiles", "the tests are green" and "it should work" are not proof. When a check fails, suspect how you observed it before the system.
- **Intent and context before code.** Restate the problem in plain words with the goal and the smallest change that meets it. Trace how the code runs now and find why it looks this way (`git log`, `git blame`, `docs/worklog.md`) before you change or delete it; say what is on record and what you infer. Reproduce a bug before fixing it; if it does not reproduce, report that and stop.
- **Subtract first, fix the root.** Remove dead code and needless layers before building. Fix the place the system first went wrong, not where the symptom shows: no guard, retry, swallowed error or clamp that only hides it. Inline one-caller wrappers and pass-through layers. Keep state narrow (returns over mutation, locals over fields) and derive instead of syncing. One decision lives in one place. Validate at the system's edges and trust internal types.
- **No speculative surface.** No feature, option, flag or extension point nobody asked for. A new internal API moves its callers and deletes the old one in the same change. Follow the code around it; add a dependency only when needed, and say why.
- **Comments.** Add none that say what the code does. In the lines you touch, delete what-comments, banners, commented-out code and TODOs. Keep a comment only for a why the code cannot show: a physical or modeling reason (why a body loses spin in water), an outside constraint (a browser, a GPU, a file format), a public API contract, a license header, a justified lint directive.
- **Checks are behavior checks.** The owner still writes its check in the same run, and it fails on the code before the change. It asserts what a player or a caller can observe (where the world is after N ticks, within a tolerance; what a real key press does), never which internal helper ran. A refactor that changes no behavior adds no check: the existing checks keep passing, and its report proves the code before and after equal once, with a bit-exact hash or the like. A bit-exact hash of floating-point state kept as a test fails when only the order of the arithmetic changes. No tests for coverage, tests pinned to internals, mock-heavy tests or new CI workflows. A new performance limit starts in observe mode: printed, not asserted. Never delete an existing test on your own; name one you think is pinned to internals as a candidate in your report.
- **Build the lever.** Unless the edit is a few obvious lines, write the small script that does or proves it (a codemod, a drive, a repro) and check it against the first unit done by hand. A CLI made for this has subcommands, a real `--help`, `--dry-run` for side effects, errors that say what to do instead, JSON output, and the same result when run twice. When the same mistake is pointed out twice, propose a check, lint or script instead of another instruction.
- **Files.** One-off scripts, renders and screenshots go outside the repo, in the session's temp or scratch folder. The verify skill's git-ignored `.verify/` is the one exception.
- **Scope.** Report a problem found outside the unit; do not fix it on the way.
- **Reports.** In this order, in plain declarative sentences: the goal, the change (with what was deleted), the proof (commands run, their key output, screenshot paths, and what could not be checked), the basis of each claim (measured, inferred or a guess), and what is left. No praise, no sign-off.
