# Repository collaboration

- For Rubber Duck Pool environment and prop art, consult `projects/rubber-duck-pool/docs/asset-art-direction.md`. The deck chair is a visual reference, not a requirement to repeat its exact colors or details on every asset.
- When creating or updating a pull request, write a specific title and a meaningful description based on the final changes. Do not leave a branch name as the title or the description empty. Explain the user-visible problem or outcome, summarize the material changes, and report checks run and important limitations. Keep the title and description current if scope changes. Do not claim a check was run when it was not.
- Follow `.github/pull_request_template.md` when it applies, adapting the detail to the change. Creating a PR does not imply permission to merge it.

# Which GPT model does what

The user set these on 2026-11-18, on top of the roles already in use: GPT-6.1 Terra builds the 3D models and GPT-6.1 Sol reviews. Carry on with the goals, scope, finished work, verification results and pending approvals already agreed, and apply this to the work that remains.

- **GPT-6.1 Terra is the default.** It takes requirements, brainstorming, planning, execution and verification, and it keeps the 3D modeling. When exploring a direction, compare candidates that take different approaches and the conditions under which each one holds. When planning, check first the assumptions that would cause the most rework if they are wrong.
- **GPT-6.1 Sol reviews**, as before.
- **GPT-6 Luna** may be used without separate approval when it can be chosen. Give it independent jobs whose scope and output format are clear, such as searching, comparing or classifying a lot of material by one set of criteria. The main model does simple checks itself.
- **GPT-6.2 Sol** may be delegated to without separate approval, one at a time. Give it reviews of important dependencies or verification gaps, or a complex implementation or root-cause analysis with a clear scope. If its result could change the order of the work, get its review before starting that work. Call it again on the same problem only with new evidence or a new question. If most of the remaining work needs it, propose switching the main model.
- **GPT-6.2 Astra only after the user's explicit approval.** It can take problem definition, design choices that are hard to reverse, and hard problems that remain after enough investigation. When matching a reference image or design pixel for pixel is the definition of done, that is Astra's job too. Ask for approval early; once approved, Astra looks at the reference image itself and makes the visual judgments and the implementation, with no earlier attempt by Terra or Sol needed. The approval request says briefly what Astra would do and what result to expect. While waiting, continue the work that does not depend on that result.
- **Delegating.** Name the model, and pass the materials, the question and the definition of done. Do not do the same work twice or delegate it again. The main model integrates and verifies the results. To check a design reproduction, compare the real result with the reference at the same viewport and screen state. If a named model cannot be used, say so and continue the work that can be done.
