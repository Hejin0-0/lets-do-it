# Rubber Duck Pool 진행 계획서

지휘하는 모델이 바뀌어도 같은 방식으로 일을 이어가기 위한 문서입니다. 지휘자는 이 문서와 `CLAUDE.md`, `docs/worklog.md`의 마지막 몇 묶음, `improvements.md`의 마지막 절을 읽고 시작합니다.

## 1. 역할 (2026-11-16 사용자 명세)

Fable은 계획과 가이드라인만 책임집니다: 이 문서, 브리프의 방향, 무엇을 고칠지와 말지의 판단. 구현, 들이기, 검증, 푸시는 Opus와 Gemini가 합니다. Fable이 없으면 통합 담당(Opus)이 이 문서대로 판단까지 맡습니다.

| 영역 | 주 담당 | 보조 | 부르는 법 |
|---|---|---|---|
| 1. 설계·맥락 (GDD와 코드 트리, 의존성과 정합성 검증, `task_spec.json`) | Gemini Argon (High) | Hydrogen | `agy -p … --model gemini-4-argon-high`. 한도가 소진되면(429) Opus가 대신합니다. |

| 2. 서브 구현 (UI 바인딩, 소리 트리거, 유닛 테스트), 계획과 검증 | GPT-6.1 Terra (High) | | `codex exec -m gpt-6.1-terra -c model_reasoning_effort='"high"' …`. 11-18부터 GPT 작업의 기본입니다(루트 `AGENTS.md`). |

단계: 1 설계(Argon) → 2A 데이터(Hydrogen) ∥ 2B 에셋(Terra) → 3A 코어 구현(Opus) ∥ 3B 서브 구현(Terra)·리뷰(Sol) → 4 QA(Sol 조작, Terra 판정). QA가 실패하면 코드 결함은 Opus로, 메시·머티리얼 결함은 Terra로 돌아갑니다.

**Terra의 에셋 절차 (네 단계, 최대 세 번 반복):**
1. 씬을 비우고(`read_factory_settings(use_empty=True)`) 명세대로 메시와 Principled BSDF 머티리얼을 만든 뒤, 트랜스폼을 적용하고 원점을 규칙(보통 바닥 가운데)에 맞춥니다.
2. 내보내기 전에 `bmesh`로 잽니다: 삼각형 수가 상한 이하, non-manifold 엣지와 면적 0인 면이 0, 노멀 방향 일관, UV 펼침.
3. 앞·옆·뒤·위 네 장(512×512 이상)을 렌더해 직접 봅니다: 뜬 부품, 뚫고 들어간 메시, 빠진 뒷면, 뒤집힌 노멀, 늘어난 UV, 치수 비율. 결함이 있으면 내보내지 않고 1로 돌아갑니다.
4. 통과하면 임시 조명과 카메라를 지우고 내보냅니다(`.glb`: `export_apply=True`, `export_yup=True`). 재현 스크립트를 저장하고 `asset_build_report.json` 하나로 보고합니다.

에셋은 `models/`와 production에 있는 완성본을 먼저 쓰고, 필요하다고 판단될 때만 새로 만듭니다. 참고 모델은 `resort-cooler-reference-v4-open`과 `deck-chair-atelier`입니다.

## 2. 한 바퀴

일은 아래 순서를 되풀이합니다. 한 바퀴는 커밋 하나로 끝납니다.

1. **찾기.** 할 일은 세 곳에서 나옵니다: Sol 리뷰의 발견, `improvements.md`의 `[남김]`, 사용자의 말. 할 일이 떨어지면 Sol에게 아직 리뷰하지 않은 영역을 맡깁니다(4절의 목록).
2. **확인.** 발견을 그대로 믿지 않습니다. 지휘자가 지목된 코드를 읽고, 플레이어가 실제로 겪는 일인지 판단합니다. 겪지 않는 일이면 `improvements.md`에 `[안 함]`과 이유를 적고 끝냅니다.
3. **나누기.** 한 단위는 원인 하나입니다. 같은 파일을 건드리는 단위는 동시에 내보내지 않습니다. 크기로 맡을 모델을 고릅니다: 한두 줄은 지휘자, 한 파일 안의 수정과 테스트는 Argon(없으면 Hydrogen), 새 구조나 여러 파일은 Opus.
4. **브리프.** 받는 쪽은 이 대화를 모릅니다. 브리프에 다음을 다 적습니다.
   - 무엇이 잘못됐고 플레이어가 무엇을 보는지, 원인이 있는 파일과 줄
   - 무엇을 바꾸고 무엇은 그대로 두는지
   - 테스트: 고치기 전 코드에서 실패해야 한다는 것과, 그것을 한 번 돌려 확인하라는 것
   - 문서: `docs/worklog.md` 끝에 다음 번호의 묶음, `improvements.md` 끝에 `[고침]` 한 줄
   - 커밋 메시지 형식과 크레딧 줄, 푸시 금지, 자기 체크아웃 밖을 건드리지 말 것
   - 마지막에 보고할 것: 커밋 해시, 바꾼 파일, 테스트 수 전후, 스스로 내린 판단
5. **체크아웃.** 에이전트마다 따로 둡니다(`$TMPDIR/agy-h`, `$TMPDIR/agy-a` 등). 시작 전에 통합 담당이 현재 브랜치 머리로 옮기고, 깨끗한지 봅니다. Agent 도구의 워크트리 격리는 origin/main에서 시작하므로 쓰지 않습니다.
6. **들이기 (통합 담당).** 에이전트의 보고가 아니라 diff를 읽습니다. 이상이 없으면 cherry-pick하고, `worklog.md` 충돌은 양쪽을 다 살리고 번호를 다시 매깁니다.
7. **증명.** 아래 셋을 다 통과해야 푸시합니다.
   - `npm run verify`의 종료 코드 0 (`&&`와 `tail`로 가리지 않습니다)
   - 브라우저 드라이브 19개(`.claude/skills/verify/drive/pool-*.js`)
   - 화면에 보이는 변화라면 전후 스크린샷과, 잴 수 있으면 숫자
8. **리뷰.** 들인 커밋을 Sol에게 보냅니다. 발견이 나오면 1로 돌아갑니다. 테스트가 약하다는 지적(고장 난 코드에서도 통과)은 수정과 같은 무게로 다룹니다.
9. **기록.** PR 본문을 고치고, 사용자에게 한국어로 짧게 알립니다.

## 3. 판단 기준

- **플레이어가 먼저입니다.** 고칠지 말지는 플레이어가 보거나 겪는지로 정합니다. 코드가 깔끔해지는 것만으로는 단위를 만들지 않습니다.
- **원인을 고칩니다.** 증상이 난 곳이 아니라 처음 틀어진 곳을 고칩니다. 같은 함수를 부르는 다른 곳도 같은 문제를 겪는지 먼저 봅니다.
- **가장 작은 변경.** 새 옵션, 새 추상화, 나중을 위한 뼈대는 넣지 않습니다. 공용 패키지(`packages/`)를 바꾸면 주지 않았을 때 전과 똑같이 동작하게 합니다(jelly의 수조 넷이 함께 씁니다).
- **테스트는 고장을 잡아야 합니다.** 새 테스트는 고치기 전 코드에서 실패하는 것을 눈으로 확인합니다. 구현이 아니라 플레이어나 호출자가 보는 결과를 단언합니다.
- **숫자에는 근거를.** 성능이나 밝기 같은 숫자는 무엇을 어떻게 쟀는지와 함께 적습니다. 기계가 바쁠 때 넘친 시간 검사는 혼자 다시 돌려 둘 다 적습니다.
- **모르면 모른다고.** 확인하지 못한 것은 통과했다고 쓰지 않습니다. 에이전트가 권한 때문에 막혔다고 하면 지휘자가 대신 돌려 주지 않고, 다른 길을 찾거나 사용자에게 알립니다.
- **묻지 않고 진행하는 것:** 되돌릴 수 있는 모든 일. **사용자의 허락이 필요한 것:** 파일 삭제, 다운로드, 범위 밖 기능, 보류 중인 것의 재개.

## 4. 범위

- **하는 것:** 한 번의 방문(풀, 오리, 앉기, 도감, 보트, 집에 가기)이 끊기지 않고 자연스러운 것. 고침, 보완, 리팩터링, 성능.
- **하지 않는 것:** 실패 상태, 타이머, 점수, 재화, 멀티플레이, 새 지역, 레이스, 꾸미기 메뉴. 합성음은 끈 채로 둡니다.
- **보류:** 시각 디자인(UI의 색, 글꼴, 모양)과 폰 레이아웃.
- **그대로 두는 것:** web-ocean에서 온 바다와 해안, 사용자의 쿨러 모델, 의자.
- **베끼지 않습니다.** 참고한 것에서는 구조와 생각만 가져옵니다.

아직 Sol이 리뷰하지 않은 영역(할 일이 떨어지면 여기서 고릅니다):
- 앉기와 카메라(`seating.js`, `navigation.js`): 앉은 채 할 수 있는 일, 일어서는 조건 (Hydrogen이 점검 중)
- 도감 화면(`book-view.js`): 키보드와 화면 읽기, 긴 목록
- 하루의 시간(`daylight.js`, 밤의 불꽃과 반딧불): 경계 시각, 동작 줄이기
- 수집품과 보트(`collectibles`, 소환, 갈매기): 드문 순서

- **배운 것:** 들이기와 검증을 한 명령으로 묶을 때는 앞 단계가 실패하면 멈추게 합니다(`&&`). 충돌 난 트리를 검증하면 결과가 뜻이 없습니다. 소리의 거리 기준은 걸어 다니는 사람이 아니라 카메라입니다. 샌드박스를 끈 명령의 `$TMPDIR`은 샌드박스 안의 `$TMPDIR`과 다릅니다. 소리 이득을 보정할 때는 옆에서 선 경우의 한 채널 피크도 잽니다. 코드가 그대로인데 드라이브가 갑자기 실패하면 Chrome 버전부터 봅니다(`/Applications/Google Chrome.app/.../Versions`). zsh에서는 `$files`가 단어로 나뉘지 않으니, 파일 목록은 `xargs`로 넘깁니다. 여러 체크아웃에서 들인 문서는 묶음 번호와 절 제목이 겹치므로 들인 뒤 한 번 정리합니다. `codex exec`를 백그라운드에서 돌릴 때는 `< /dev/null`로 표준 입력을 닫습니다. 닫지 않으면 "Reading additional input from stdin..."에서 끝없이 기다립니다(11-17 리뷰가 23분 멈춤). `resolve-docs.py`는 들이는 쪽 묶음 번호를 이미 다시 매기므로, 번호를 고치는 `sed`는 고칠 줄을 찾았는지 확인한 뒤 줄 번호를 붙여서만 돌립니다(찾지 못해 줄 번호가 비면 `sed`가 모든 줄에 적용됩니다, 11-17). 성능 예산 테스트(jelly의 melon 단계 비용)는 에이전트 셋이 함께 돌 때 넘칠 수 있으니, 실패하면 다른 작업이 없을 때 다시 돌려 확인합니다.

## 6. 지휘자의 검증 기준

사용자가 2026-11-15에 준 기획팀 매뉴얼과 이미지 넷입니다. 만드는 쪽이 아니라 지휘자가 결과를 볼 때 쓰는 잣대입니다. 단위를 들일 때(2절의 6·7단계)와 새 기능을 정할 때 이 절을 봅니다.

### 6.1 순서와 일곱 역할

컨셉 → 게임 → 시나리오 → 밸런스 → 레벨 → UI ⇄ 그래픽 → 봇 검증 → 교차 검토 → 배포. 뒤 단계의 결과가 앞 단계의 결정과 어긋나면 뒤를 고칩니다.

| 역할 | 검증 질문 | Rubber Duck Pool에서 보는 것 |
|---|---|---|
| 컨셉 | 30초 안에 설명되나? 화면 한 장으로 재미가 보이나? | `design/game-brief.md`의 한 줄 소개, 핵심 감정, 이 게임이 아닌 것(4절) |
| 게임 | 질문 없이 만들 수 있나? 예외를 다 적었나? 3분 안에 재미를 느끼나? | 한 번의 방문 흐름, 손·앉기·도감·보트의 규칙과 예외 |

| 밸런스 | 숫자마다 근거가 있나? 하나만 쓰면 되는 선택이 있나? | 도착 간격(10–20초), 뜻밖의 오리 비율(1/4), 방문당 만나는 수. 전투·재화·가챠·과금은 이 게임에 없습니다. |

### 6.2 전원이 지킬 원칙 (교차 검토 목록)

- **게슈탈트:** 가까운 것은 한 묶음으로 읽힙니다(근접성). 빈칸은 채우고 싶어집니다(폐쇄성: 도감의 빈 쪽). 대칭은 공정, 비대칭은 긴장입니다. 익숙한 형태가 먼저 읽힙니다. 원칙끼리 부딪치면(가까운데 색이 달라 묶음이 헷갈림) 지적합니다.
- **자이가르닉:** 페이지를 닫을 때 끝내지 못한 일이 하나 이상 남아야 합니다(보트가 가져오는 중인 물건, 아직 못 만난 오리). 그것은 기대여야 하고 불안이면 안 됩니다. 놓치면 손해라는 압박과 다크패턴은 쓰지 않습니다. 동시에 남는 일은 3–5개까지입니다.
- **피츠:** 자주 누르는 것은 크고 가깝게(44pt 이상), 위험한 것(처음부터 다시, 돌려보내기)은 작고 멀리 둡니다.
- **힉:** 한 화면의 주요 선택은 3–5개까지이고, 나머지는 단계적으로 엽니다.
- **카이와:** 이 게임은 미미크리(역할: 풀가의 손님)가 주, 알레아(운: 어떤 오리가 올지)가 보조이고, 파이디아(자유로운 놀이) 쪽에 있습니다. 운 요소는 확률을 숨기지 않고, 과금이 없으니 도박이 될 길이 없습니다. 경쟁(점수, 레이스)을 들이면 이 좌표가 깨집니다.
- **논문 다섯:** MDA(느낌을 먼저 정하고 규칙을 역산), GameFlow(집중·도전·통제·목표·피드백을 1–5점으로 자가 평가), Jenkins(이야기는 공간에 심고, 핵심 정보는 세 곳에 겹쳐 둠), SDT(자율성·유능감·관계성. 보상은 정보로 주고 통제로 주지 않음), DDA(헤매는 것을 감지하면 티 나지 않게 필요한 만큼만 도움).

### 6.3 데이브 3원칙

1. **재미는 객관적으로 잽니다.** 주변의 "재밌다"는 믿지 않습니다. 개발자가 끼어들지 않는 시험만 근거로 칩니다. 이 저장소에서는 드라이브와 `pool-fuzz`, Sol의 재현이 그 자리이고, 사람 시험이 없다는 것은 보고에 그대로 적습니다.
2. **남들과 달라야 합니다.** "이것에 돈을 쓰겠나?"를 묻습니다. 장르, 아트, 세계관, 완성도, 타이밍 가운데 한두 가지는 확실히 달라야 합니다. "~ 느낌 난다"는 칭찬이 아닙니다. 새 기능은 이 게임만의 것(물 위의 오리를 손으로 다루는 느낌, 하루가 흐르는 풀)을 굵게 하는지로 고릅니다.
3. **겸손해야 합니다.** "이 정도면 괜찮다"가 오만입니다. 플레이어가 막히면 플레이어를 탓하지 않고 막히는 지점을 없앱니다. 그렇다고 모든 의견을 받지는 않습니다(4절의 범위가 중심입니다).

### 6.4 글: Simplified Technical English

페이지에 나오는 영어와 영어로 쓰는 브리프에 적용합니다.

- 절차 문장은 20단어, 설명 문장은 25단어까지. 한 문장에 지시 하나. 문단은 여섯 문장까지, 문단 하나에 주제 하나.
- 쉬운 낱말을 씁니다: start(commence 아님), make sure(ensure 아님), before(prior to 아님), use(utilize 아님), about(approximately 아님), fill(replenish 아님), to(in order to 아님).
- 같은 것은 늘 같은 낱말로 부릅니다. 한 낱말은 한 뜻과 한 품사로만 씁니다.
- 지시는 명령형 능동태로 씁니다. 진행형(-ing)과 완료형, 절차 속 수동태는 쓰지 않습니다.
- 관사(the, a)와 this를 빼지 않습니다. 명사를 넷 이상 잇대지 않습니다.
- 경고는 명령을 먼저, 위험을 다음에 씁니다.

### 6.5 매뉴얼과 기존 지시가 부딪치는 곳

- 매뉴얼의 전투·성장·경제·가챠·과금·광고·스테이지는 이 게임의 범위 밖입니다(4절). 해당 항목은 "없음"으로 통과시킵니다.
- 매뉴얼은 그래픽을 ChatGPT 웹으로 만들라고 하지만, 이 프로젝트의 에셋은 Terra Max가 만들고 Blender는 지휘자가 돌립니다(1절). 사용자가 바꾸라고 하기 전에는 1절을 따릅니다.
